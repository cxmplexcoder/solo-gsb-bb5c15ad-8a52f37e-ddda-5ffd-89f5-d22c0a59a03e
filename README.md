# 陶瓷窑车层架载荷追踪台

用 **Python Flask + 原生 JavaScript** 构建的窑车装架载荷追踪工具。自下而上录入每一层
矩形棚板的位置、棚板自重、坯件重量，以及承托该层棚板的立柱坐标与容量；系统根据坐标
判定每根立柱的脚落在哪块下层棚板（或窑车台面）上，再**逐层向下分摊并累加载荷**，
在俯视图与侧视图中标出 **悬空 / 落点重叠 / 超载** 立柱，并可查看每根立柱的完整
**载荷来源**。修改任意一层后整架结果自动同步重算。

---

## 一条命令启动

```bash
docker compose up --build -d
```

然后浏览器访问：

> **http://localhost:8000**

依赖（Flask、gunicorn）随镜像安装，示例数据 `data/sample.json` 随镜像内置并在
打开页面时自动载入，无需任何额外步骤。

停止 / 查看日志：

```bash
docker compose down
docker compose logs -f
```

> 首次启动需要联网拉取 `python:3.11-slim` 基础镜像并安装依赖，之后再次启动为秒级。

## 必要配置（`docker-compose.yml`）

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `ports` 宿主机端口 | `8000:8000` | 左侧宿主机端口可改，例如 `9000:8000` 后访问 `http://localhost:9000` |
| `PORT`（容器内） | `8000` | gunicorn 监听端口；如修改需与 `ports` 右侧一致 |
| `SAMPLE_PATH` | `/srv/data/sample.json` | 启动时自动载入的示例数据路径 |
| `volumes` | `./data:/srv/data:ro` | 把宿主机 `data` 目录挂入容器，**替换或编辑挂载目录中的 `sample.json` 后重启容器即可更换内置示例** |
| `restart` | `unless-stopped` | 容器退出时自动重启 |

不使用 Compose 也可以直接用 Docker：

```bash
docker build -t kiln-cart-load-tracker .
docker run --rm -p 8000:8000 -v "$PWD/data:/srv/data:ro" kiln-cart-load-tracker
```

## 界面与操作

页面分左右两栏，所有修改均在前端防抖后自动调用 `POST /api/compute` **整架重算**
（约 200 ms 去抖，无需保存按钮）。

**左栏 · 录入（自下而上）**

- 窑车台面宽（X）/ 深（Y）、落点重叠判定容差（长度单位，0 表示坐标必须完全相同）。
- 每层一张卡片，可增删层、在层级间上下移动；每层包含：
  - 棚板左下角坐标 `(x, y)`、宽 `width`（X 向）、深 `height`（Y 向）；
  - 棚板自重 `shelf_weight`、坯件重量 `ware_weight`（kg）；
  - 承托本层棚板的立柱列表：**柱脚坐标 `(x, y)`** 与单柱容量 `capacity`（kg）。
  - 层卡片按自下而上排列；第 1 层立柱的脚落在窑车台面上，第 i 层立柱的脚
    落在第 i−1 层棚板上。
- 「导出 JSON」可下载当前模型，方便保存或替换 `data/sample.json`。

**右栏 · 视图与结果**

- **俯视图（X–Y）**：虚线灰框为窑车台面，蓝框为各层棚板（越靠上越浓），圆点为立柱：
  - 绿色＝正常，红色＝超载，橙色＝落点重叠（带虚线圈），紫色虚线＝悬空；
  - 顶部层标签可点击，用于显隐某层；
  - 悬停显示坐标、落点、反力、容量、利用率，**点击立柱查看载荷来源**。
- **侧视图（X–Z / Y–Z）**：可切换观察方向；灰色粗线为台面，蓝色横线为棚板，
  竖线为立柱（颜色规则同俯视图；悬空柱画成紫色虚线；侧视投影重叠的立柱小幅错开）。
- **立柱载荷来源表**：列出分摊到该柱的每一项——本层棚板自重、本层坯件、
  上层各柱压入的反力，给出各项来源毛重与本柱分摊额，末行为反力合计。
- **逐层载荷汇总表**：每层棚板自重 / 坯件 / 上层压入 / 本层毛重 / 有效立柱数 /
  单柱反力 / 状态；点击某行可在俯视图中定位该层。
- 页面顶部黄色横幅汇总检出的超载、重叠、悬空与失支撑层。

内置示例 `data/sample.json` 故意包含三类问题，便于直接观察：
中层一根柱头顶出棚板（悬空）、两根同坐标立柱（落点重叠）、顶层 4 根立柱均超载。

## 载荷模型与判定规则

```
本层毛重 gross = 棚板自重 + 坯件重量 + 上层所有“有效立柱”反力之和
单根有效立柱反力 = gross / 本层有效立柱数
```

立柱从顶层向最底层逐层计算：顶层立柱反力压入下一层棚板，成为下一层“上层压入”，
与该层棚板自重、坯件重量合并后再由该层立柱均摊，如此一直下传到窑车台面。

一根立柱判定为**有效支撑**需同时满足：

1. **柱脚在下层承载面上**：第 1 层在窑车台面 `[0, 宽]×[0, 深]` 内，
   第 i 层在第 i−1 层棚板矩形内（含边界）；否则标记 **悬空**；
2. **柱头顶在所承托的本层棚板内**：柱坐标位于本层棚板矩形内，否则同样标记 **悬空**。

- **悬空柱不承担载荷**，本层毛重改由其余有效立柱平均分摊；若一层没有任何有效立柱，
  该层标记为「失去支撑」，其载荷无法继续下传。
- **落点重叠**：同层两根立柱柱脚坐标相同（两点距离 ≤ 重叠容差）即判为重叠组，
  在俯视图用橙色虚线圈标出；重叠柱仍按各自容量独立参与分摊。
- **超载**：有效立柱分摊到的反力大于其容量即标红；利用率与超载量在悬停提示、
  载荷来源面板和横幅中给出。

长度单位可统一视为 cm（仅用于包含判定与绘图比例），重量单位为 kg；
只要同一架次内单位统一即可。

## 数据模型（API / JSON）

`POST /api/compute` 请求体（即导出的 JSON）：

```json
{
  "deck": { "width": 200, "depth": 120 },
  "overlap_tolerance": 0,
  "layers": [
    {
      "name": "底层",
      "x": 5, "y": 5, "width": 190, "height": 110,
      "shelf_weight": 80, "ware_weight": 72,
      "columns": [
        { "x": 15, "y": 15, "capacity": 130 }
      ]
    }
  ]
}
```

`layers` 必须**自下而上**排列；字段均为数字。响应在原结构基础上为每层与每根立柱
附加 `gross / share / load / status / supported / overlap / overloaded /
landing_detail / sources / warnings` 等字段。非法输入返回
`{"ok": false, "errors": [...]}`，前端保留上一次有效结果并在红条中列出原因。

其他接口：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/` | 前端页面 |
| GET | `/api/sample` | 读取内置示例数据 |
| POST | `/api/compute` | 提交整架模型，返回载荷结果 |
| GET | `/healthz` | 健康检查（容器 HEALTHCHECK 使用） |
